# Decipher Integration Guide (Survey Programmers)

This guide explains how to add bot detection to a Decipher (Forsta) survey. There are two ways:

- **Recommended: add tracking on the dashboard (Part A).** Upload the survey XML on the Add tracking page. The service adds the tracker and a set of hidden `QOS_` result questions, and you upload the tracked survey to Decipher in one click (or download it and import it yourself). No JavaScript to copy.
- **Alternative: build it yourself with the API (Part B).** Add your own JavaScript that creates a session, sends behaviour events and asks for an analysis at the end. Use this only if you cannot use the XML route.

# Part A: Add tracking on the dashboard (recommended)

## A1) What you need

- The survey XML. In Decipher, open the survey's XML editor and copy or download the whole file. It must be a complete survey: the top element is `<survey ...>`.
- For one-click upload: a Decipher API key saved on the service. An admin enters `DECIPHER_API_KEY` on the dashboard's Settings page (unlock it with the admin token), or sets it as an environment variable. Without a key you can still download the tracked file and import it by hand.

## A2) Add tracking

1. Open **Set up > Add tracking** (`index.html#/tracking`).
2. Choose the survey XML file (a `.xml` file, or a `.txt` file holding the XML, up to 5 MB), or drop it on the page.
3. **Survey id (optional).** This groups the survey's responses on the dashboard. Leave it empty to use the survey title. If the file already has tracking, its id is kept unless you enter a different one.
4. **Options:**
   - **Show a privacy notice on the first page** (on by default). Tells respondents that the survey checks how answers are entered. Leave the text empty for the default wording, or write your own (up to 400 characters, no `$` or square brackets).
   - **End the survey on a clear bot signal** (off by default). Choose the page whose submit runs the check, and which signals end the survey (all seven are ticked by default):
     - **Automated or headless browser**: the browser reports that it is controlled by automation software, or its user agent belongs to a headless or automated browser.
     - **Clicks and key presses generated by script**: at least half of the clicks and key presses (and at least 3) are marked by the browser as not made by a person.
     - **Pages answered with no mouse or keyboard use**: on a computer (not a phone or tablet), two or more pages were answered with no mouse movement, clicks or key presses, or with several clicks but no mouse movement and no key presses.
     - **Hidden honeypot field filled in**: a text box placed off screen, labelled "Leave this empty", that people never see or reach with the Tab key, was filled in. It has no name, so it never reaches the Decipher data.
     - **Open ends that appeared without typing**: open-ended answers that appeared without any typing, pasting or dictation.
     - **Typing or mouse movement with machine-exact timing**: typing whose gaps between key presses vary by less than 3 ms in at least three separate stretches of 8 or more keys, or mouse movement made of ruler-straight runs of exactly equal steps covering a large share (40% or more) of the mouse path. Holding Backspace down never counts.
     - **Page times longer than the time the server saw**: the page times the browser reports add up to at least a minute and are clearly longer (by more than 30 seconds and more than 25%) than the time between the session starting and its last event reaching the service. Page times are measured in the browser and can be made up; the service's own clock cannot.

     A score alone never ends the survey. Only page breaks every respondent reaches count (not inside loops or conditional blocks). If the check cannot reach the service, the respondent carries on.
5. Click **Add tracking**. The page shows what was added, the survey id, the number of questions and pages, and any warnings.

## A3) Get the tracked survey into Decipher

After tracking is added, either:

- **Upload to Decipher** (when an API key is set). Pick one target:
  - **Update the survey uploaded last time** (shown when this survey id was uploaded before),
  - **Create a new Decipher survey** named after the survey id, or
  - **Replace the XML of an existing survey**: paste its path (for example `selfserve/53b/240101`) or its link.

  Decipher checks the file before saving it and never replaces the XML of a live survey. If the survey has saved data layouts, the `QOS_` variables are added to them. When the upload works you get a link to open the survey.
- **Download** the tracked file, then in Decipher open the survey's XML editor, replace the XML with the downloaded file, and save.

To change the options later, upload the tracked file again. The existing tracking is replaced, not added twice. Files tracked by Quant OS are recognised the same way.

## A4) What gets added

Nothing else in the survey changes, and removing the tracking gives back the original file exactly.

- **The tracker script**, added as a `respview.client.js` style with `mode="after"`, so it runs alongside any page scripts the survey already has.
- **Decipher's `uuid` as the respondent id**, so every session can be matched to a record in Decipher's data.
- **A final page of hidden `QOS_` questions** that the tracker fills in before the respondent submits:
  `QOS_RESPONDENT`, `QOS_SESSION`, `QOS_FLAG`, `QOS_SCORE`, `QOS_RISK`, `QOS_STATUS`, `QOS_BEHAV`, `QOS_OES`, `QOS_FRAUD`, `QOS_DUP`, `QOS_DUP_SCORE`, `QOS_IP_RISK`, `QOS_DEVICE_RISK`, `QOS_GEO_RISK`, `QOS_VELOCITY`, `QOS_DATACENTER`, `QOS_SPEEDER`, `QOS_STRAIGHTLINE`, `QOS_FLAGCOUNT`, `QOS_REASON`, `QOS_REASONS`.
- **`QOS_privacy`**: the privacy notice, if chosen.
- **`QOS_EARLY` and `QOS_bot_term`**: the in-survey check and the termination, if you chose to end the survey on a clear bot signal.

### What the `QOS_` values mean

The values follow the survey's own quality rules on Live Quality (bot threshold, which bot signals count, whether data-centre IPs and which open-end problems are flagged, the seconds-per-page speeder rule), so a respondent gets the same verdict in the Decipher data as on the dashboard. A value is left blank when its check had nothing to work on. Scores are whole numbers from 0 to 100; `QOS_OES` is a quality score (higher is better), every other score is a risk (higher is worse).

| Variable | Meaning |
|----------|---------|
| `QOS_STATUS` | 1 human, 2 suspect (any reason code, or medium risk or above), 3 bot. Bot or human is decided by behaviour only; open ends and fraud show in their own variables. |
| `QOS_BEHAV` | Behaviour bot score |
| `QOS_OES` | Average quality of the open-ended answers that were checked |
| `QOS_FRAUD` | Fraud score |
| `QOS_DUP` | 1 when the device, IP address or answers were seen on other sessions |
| `QOS_DUP_SCORE` | Duplicate risk: the highest of the device reuse, IP reuse and duplicate-answer risks (not the raw text similarity) |
| `QOS_IP_RISK`, `QOS_DEVICE_RISK`, `QOS_GEO_RISK`, `QOS_VELOCITY` | IP address, device reuse, location mismatch and survey-taking speed risks |
| `QOS_DATACENTER` | 1 when the IP address belongs to a data centre, VPN or proxy (only when the survey's rules flag data-centre IPs) |
| `QOS_SPEEDER` | Pages answered too fast: the number of pages answered in less time than the survey's seconds-per-page rule |
| `QOS_STRAIGHTLINE` | Number of straight-lined grid questions |
| `QOS_FLAGCOUNT` | Number of reason codes |
| `QOS_REASON` | The main (lowest-numbered) reason code, 0 for none |
| `QOS_REASONS` | Every reason code, comma-separated |

Reason codes (only bot signals the survey's rules switch on are used):

| Code | Reason |
|------|--------|
| 1 | Automated or headless browser |
| 2 | Clicks and key presses generated by script |
| 3 | Pages answered with no mouse or keyboard use |
| 4 | Hidden honeypot field filled in |
| 5 | Open ends that appeared without typing |
| 6 | Bot-like behaviour score (a bot with none of the signals above) |
| 7 | Typing or mouse movement with machine-exact timing |
| 8 | Page times longer than the time the server saw |
| 10 | Data centre, VPN or proxy IP address |
| 11 | Same device seen on other sessions of this survey |
| 12 | Same IP address used repeatedly |
| 13 | Answers copied from another respondent |
| 14 | Many surveys started in a short time |
| 15 | Same respondent seen from different countries within an hour |
| 20 | Low-quality open-ended answers |
| 21 | Straight-lined grid questions |
| 22 | Questions answered too fast (pages average less time than the survey's seconds-per-page rule) |

Good to know:

- **Open ends that could not be checked.** If the AI check is unavailable or busy, an answer waits up to 20 seconds for a turn. If it still cannot be checked it is marked as not checked: it gets no quality score, is not counted in `QOS_OES` (blank if none of the respondent's answers could be checked), and is not flagged. It is never treated as an acceptable answer. Live Quality's CSV export counts them per respondent (`text_unchecked`).
- **Straight-lining** means the same answer on every row of a grid with at least 3 rows.
- **The location check** (`QOS_GEO_RISK`, reason 15) needs an IP-to-country lookup the service does not have yet, so it is left out of the fraud score for now.

### Signed tracking

The tracker calls the service's API address (`TRACKER_API_BASE`, or else the address the upload came in on; it must be https except on localhost). Signing with `TRACKING_TOKEN_SECRET` is optional; the Add tracking page says whether the tracked file is signed. When it is set, the tracker carries a token for the survey id, and a survey that requires signed sessions refuses sessions without it. A survey starts requiring them as soon as a signed tracked file is uploaded to Decipher with **Upload to Decipher** (or when its first signed respondent arrives). Downloading the tracked file alone does not switch this on, because the live survey may still run an older, unsigned tracker. The token keeps out people who never saw the survey; anyone who opens the survey page can read it. **Set the secret once.** Changing it later makes the tokens in surveys already live invalid, and every respondent of those surveys is refused until each survey is tracked and uploaded again.

## A5) What Decipher refuses, and how to fix it

The service checks for survey settings Decipher refuses before anything is sent. Add tracking still works, but shows a warning that starts with "Decipher will refuse this file:". **Upload to Decipher** stops with "nothing was sent to Decipher", so no empty survey is created.

| Problem | Why | Fix |
|---------|-----|-----|
| No `compat` on the `<survey>` tag | Decipher reads it as compat 0, which it no longer accepts | Export the XML from Decipher (it always includes one), or add `compat="155"` |
| `compat` below 143 | Decipher has retired those compat levels | Update the survey's compat in Decipher, then export again |
| `compat` 151 or higher without `delphi="1"` | Decipher requires `delphi="1"` from compat 151 | Export from Decipher, or add `delphi="1"` to the `<survey>` tag |
| Only the body of a survey (no `<survey>` element) | Not a complete survey; refused as not well-formed | Export the whole survey XML |
| The survey uses quota sheets, data files (`File("x.dat")`) or `${res.X}` resources | Those files live in the original Decipher survey, not in the XML, so a new survey lacks them and Decipher's checks fail | Upload into the original survey (or a copy of it) with **Replace the XML of an existing survey** |
| The survey already has its own `QOS_` labels | They would clash with the added ones | Rename them first |

Decipher's own error messages, including script errors such as `Exec (page N): ...`, are shown in full. If an upload fails after a new survey was created, the message gives that survey's path; uploading again after a fix updates it.

## A7) Where the results appear

- **Live Quality** (`index.html#/quality`): one view per survey with bots, flags (bot-like behaviour, low-quality open ends, pasted answers, straight-lining, speeder, flatliner, duplicate, high fraud risk, data-centre IP), trends and one row per respondent. You can set rules per survey and export a CSV; the CSV's `text_unchecked` column gives each respondent's open ends that could not be checked. In the results from the API (`GET /api/v1/quality/results`), a respondent with several sessions (the same Decipher `uuid`) counts once in `totals.respondents`, `totals.sessions` counts every session, and each row's `other_sessions` says how many more sessions that respondent has. The **Live quality and rules** link on Add tracking opens it for your survey.
- **Decipher data exports**: the `QOS_` columns, filled in when the respondent submits the final page.
- **`LQ_` variables in your own data file**: on Live Quality, use **Add flags to a data file** to upload a `.sav`, `.csv` or `.xlsx` file (up to 50 MB). You get the same file back with `LQ_` variables (verdict, scores and one 0/1 per flag), matched on `QOS_SESSION`, then `QOS_RESPONDENT`, then Decipher's `uuid`. When one `uuid` has several sessions (for example the respondent left and came back), a session that has been checked is used first, then the latest one, rather than an abandoned earlier one. These follow the survey's current Live Quality rules; the `QOS_` values in Decipher do not change.
- **Overview, Sessions and the survey dashboard** (`index.html#/surveys/<survey id>`) also list the sessions.

## A8) The same steps with the API

- `GET /api/v1/tracking/decipher/options`: the signals, the default privacy text, whether signing is on, whether Decipher upload is configured, and the upload limit.
- `POST /api/v1/tracking/decipher`: multipart `file`, with form fields `survey_id`, `terminate`, `after_page`, `signals`, `privacy_notice`, `privacy_text`. Add `?format=xml` to get the tracked file itself.
- `POST /api/v1/tracking/decipher/upload`: JSON `{"xml", "survey_id", "survey_path", "create_new"}` to create a survey, or to replace the `survey.xml` of a given path or of the path used last time for that survey id.

## 2) Create a Bot Detection Session (Survey Start)

Create a session when the respondent starts your survey. Store the returned `session_id` in a Decipher variable (e.g., `session_id`). You can do this in a pre-load script on your first page or a custom initialization question.

**Recommended:** Include `survey_id`, `respondent_id`, and `platform_id` parameters for hierarchical tracking and aggregation.

Example (custom JavaScript, runs once at start):

```javascript
const API_BASE = 'https://bot-backend-119522247395.northamerica-northeast2.run.app/api/v1';

// Get survey identifiers from Decipher
const surveyId = getIdentifierValue('survey_id') || 'decipher_survey_123';
const respondentId = getIdentifierValue('respondent_id') || 'resp_' + Date.now();
const platformId = 'decipher'; // Platform identifier

async function createBotSession() {
  // Create session with survey metadata for hierarchical tracking
  const url = `${API_BASE}/detection/sessions?survey_id=${encodeURIComponent(surveyId)}&respondent_id=${encodeURIComponent(respondentId)}&platform_id=${encodeURIComponent(platformId)}`;
  const resp = await fetch(url, { method: 'POST' });
  const data = await resp.json();
  // Save session_id to a hidden question or Decipher variable
  // Example: write to a hidden input with id "session_id"
  document.getElementById('session_id').value = data.session_id;
}

createBotSession().catch(console.error);
```

**Note:** The `platform_id` parameter enables hierarchical data access. You can later query aggregated metrics at the survey, platform, and respondent levels using the hierarchical API endpoints.

Hidden question HTML example (Decipher page):

```html
<input type="hidden" id="session_id" name="session_id" value="">
```

## 3) Add the Event Tracker (During Survey)

Capture keystrokes, mouse, focus/blur, scroll, and device info. Send batched events to the API to minimize network overhead.

```javascript
const API_BASE = 'https://bot-backend-119522247395.northamerica-northeast2.run.app/api/v1';
const BATCH_SIZE = 20;
const FLUSH_MS = 3000;

let eventBuffer = [];
let flushTimer = null;

function getSessionId() {
  const el = document.getElementById('session_id');
  return el ? el.value : null;
}

function queueEvent(evt) {
  eventBuffer.push(evt);
  if (eventBuffer.length >= BATCH_SIZE) {
    flushEvents();
  } else if (!flushTimer) {
    flushTimer = setTimeout(flushEvents, FLUSH_MS);
  }
}

async function flushEvents() {
  clearTimeout(flushTimer);
  flushTimer = null;
  if (eventBuffer.length === 0) return;

  const sessionId = getSessionId();
  if (!sessionId) return; // not ready yet

  const payload = eventBuffer.slice();
  eventBuffer = [];

  try {
    await fetch(`${API_BASE}/detection/sessions/${sessionId}/events`, {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify(payload)
    });
  } catch (e) {
    // On failure, re-queue once to avoid data loss
    eventBuffer = payload.concat(eventBuffer);
  }
}

// Keystrokes
document.addEventListener('keydown', (e) => {
  queueEvent({
    event_type: 'keystroke',
    timestamp: new Date().toISOString(),
    key: e.key,
    key_code: e.keyCode,
    element_id: e.target && e.target.id
  });
});

// Mouse movement (throttled)
let lastMouseTs = 0;
document.addEventListener('mousemove', (e) => {
  const now = Date.now();
  if (now - lastMouseTs < 100) return; // throttle 10/s
  lastMouseTs = now;
  queueEvent({
    event_type: 'mouse_move',
    timestamp: new Date().toISOString(),
    x: e.clientX,
    y: e.clientY
  });
});

// Scroll (throttled)
let lastScrollTs = 0;
document.addEventListener('scroll', () => {
  const now = Date.now();
  if (now - lastScrollTs < 200) return;
  lastScrollTs = now;
  queueEvent({
    event_type: 'scroll',
    timestamp: new Date().toISOString(),
    delta_y: window.scrollY
  });
}, { passive: true });

// Focus/Blur
document.addEventListener('focusin', (e) => {
  queueEvent({
    event_type: 'focus',
    timestamp: new Date().toISOString(),
    element_id: e.target && e.target.id
  });
});
document.addEventListener('focusout', (e) => {
  queueEvent({
    event_type: 'blur',
    timestamp: new Date().toISOString(),
    element_id: e.target && e.target.id
  });
});

// Device info (once)
queueEvent({
  event_type: 'device_info',
  timestamp: new Date().toISOString(),
  screen_width: window.screen.width,
  screen_height: window.screen.height,
  user_agent: navigator.userAgent
});

// Ensure buffer is flushed before page unload
window.addEventListener('beforeunload', () => { flushEvents(); });
```

Place the above on a shared header template or relevant pages to ensure coverage across the study.

## 3b) Grid/Matrix Question Capture (Optional)

To enable **grid/matrix analysis** (straight-lining, response patterns, variance), capture grid questions as follows.

**1. Register the grid when it is shown**  
Call `POST /text-analysis/questions` once per grid with `question_type: 'grid'` or `'matrix'`. Store the returned `question_id` (e.g. in a variable keyed by your Decipher question/variable name).

**2. When the respondent has completed the grid** (e.g. on "Next" or page leave), collect each selected value (one per cell) and send **one** `POST /text-analysis/responses` **per cell** with that same `question_id`, `response_text` = the cell value (e.g. `"1"`, `"5"`), and optionally `response_time_ms` for the grid.

Example – register grid question:

```javascript
async function registerGridQuestion(questionText, elementId) {
  const sessionId = document.getElementById('session_id')?.value; // or bot_session_id
  if (!sessionId) return null;
  const resp = await fetch(`${API_BASE}/text-analysis/questions`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({
      session_id: sessionId,
      question_text: questionText || 'Grid question',
      question_type: 'grid',
      element_id: elementId || '',
      page_url: window.location.href,
      page_title: document.title
    })
  });
  const data = await resp.json();
  return data.question_id;
}
```

Example – send grid cell values (one request per cell):

```javascript
async function sendGridResponses(questionId, responseTimeMs, cellValues) {
  const sessionId = document.getElementById('session_id')?.value;
  if (!sessionId || !questionId || !cellValues?.length) return;
  for (const value of cellValues) {
    await fetch(`${API_BASE}/text-analysis/responses`, {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({
        session_id: sessionId,
        question_id: questionId,
        response_text: String(value),
        response_time_ms: responseTimeMs || null
      })
    });
  }
}
```

Get `cellValues` from your grid DOM (e.g. collect each selected input/radio value in row order) or from Decipher’s JS API if available. Grid analysis runs when you call the composite-analyze endpoint on completion (see section 4).

## 4) Trigger Analysis (On Completion)

On the final page or submit event, call the analysis endpoint. **Recommended:** use **composite-analyze**, which combines behavioral, text quality, fraud, grid, and timing analysis. You can also check readiness first via `ready-for-analysis`.

**Composite analyze (recommended)** – includes behavioral + text quality + fraud + grid + timing:

```javascript
async function analyzeSession() {
  const sessionId = document.getElementById('session_id').value; // or bot_session_id
  if (!sessionId) return;

  // Optional: ensure session is ready for analysis
  const readyResp = await fetch(`${API_BASE}/detection/sessions/${sessionId}/ready-for-analysis`);
  const ready = await readyResp.json();
  if (!ready.is_ready) {
    await flushEvents();
  }

  // Composite analyze: behavioral + text quality + fraud + grid + timing
  const resp = await fetch(`${API_BASE}/detection/sessions/${sessionId}/composite-analyze`, {
    method: 'POST'
  });
  const result = await resp.json();
  document.getElementById('bot_result').value = JSON.stringify(result);
  // Optional: save is_bot, composite_score, etc. to separate hidden fields
}

// Call analyzeSession on final submit / thank-you page
```

What the result says: `is_bot` is decided by behaviour only, judged by the survey's quality rules (its bot threshold and the bot signals it switches on), so it matches Live Quality. Text quality and fraud are reported as their own scores and flags. `composite_is_bot` says whether the combined score alone reached the threshold, and `behavioral_details.engine_is_bot` gives the verdict under the service-wide threshold. `survey_variables` holds the `QOS_` values described in Part A.

**Behavioral-only analyze** – if you only need keystroke/mouse/scroll analysis:

```javascript
const resp = await fetch(`${API_BASE}/detection/sessions/${sessionId}/analyze`, { method: 'POST' });
const result = await resp.json();
```

Hidden field for storing results:

```html
<input type="hidden" id="bot_result" name="bot_result" value="">
```

## 7) Troubleshooting

- Blank page or no events: ensure the tracker script loads on each survey page and `session_id` is populated before events are flushed.
- 403/401 errors: confirm the API URL is correct and reachable; check corporate proxy rules.
- CORS errors in console: our backend allows public requests; if using a custom domain, ensure CORS origins include your domain.
- Large respondents: increase `BATCH_SIZE` or lower throttle for high-interaction pages.

## 8) Security & Privacy Notes

- Do not capture PII in raw events. Only capture interaction metadata needed for behavioral analysis.
- The tracker never sends answers from text boxes that ask for an email address, phone number, name, address, postcode, date of birth or government id, and sends page addresses without their query string. The service applies the same rules on arrival (answers to such questions are not stored; emails and phone numbers in other open ends are masked before the AI text check). Wording that doesn't match the list (for example "How can we reach you?") is not recognised, so keep contact questions worded plainly or outside tracked pages.
- Transport is HTTPS; data at rest is stored in Cloud SQL.
- If you need to disable specific event types for a page (e.g., open-ended PII), wrap listeners with page-level guards.

## 9) Hierarchical API Access

With `platform_id` included in session creation, you can access aggregated data through the hierarchical API:

### Get Respondent Summary
Aggregate all sessions for a respondent:
```javascript
const surveyId = 'decipher_survey_123';
const platformId = 'decipher';
const respondentId = 'resp_789';

const url = `${API_BASE}/surveys/${surveyId}/platforms/${platformId}/respondents/${respondentId}/summary`;
const response = await fetch(url);
const summary = await response.json();
// Returns: total_sessions, bot_rate, avg_confidence, overall_risk, etc.
```

### List All Sessions for a Respondent
```javascript
const url = `${API_BASE}/surveys/${surveyId}/platforms/${platformId}/respondents/${respondentId}/sessions`;
const response = await fetch(url);
const sessions = await response.json();
// Returns: Array of all sessions with detection results
```

### Get Survey-Level Aggregation
```javascript
const url = `${API_BASE}/surveys/${surveyId}`;
const response = await fetch(url);
const surveyData = await response.json();
// Returns: Aggregated metrics for entire survey across all platforms and respondents
```

### Get Text Analysis Summary (Hierarchical V2)
Access text quality analysis at different hierarchy levels.

**Good to know:**
- If you only have a `session_id`, you can use the **flat** session summary endpoint: `GET /api/v1/text-analysis/sessions/{sessionId}/summary`
- If you have `survey_id`/`platform_id`/`respondent_id`, use the **hierarchical** V2 endpoints below for aggregated views.

```javascript
// Session-level text analysis summary (flat; requires only sessionId)
const flatSessionSummaryUrl = `${API_BASE}/text-analysis/sessions/${sessionId}/summary`;
const flatSessionSummaryResp = await fetch(flatSessionSummaryUrl);
const flatSessionSummary = await flatSessionSummaryResp.json();
// Returns: session-level text quality summary

// Survey-level text analysis summary
const surveyTextUrl = `${API_BASE}/surveys/${surveyId}/text-analysis/summary`;
const surveyTextResponse = await fetch(surveyTextUrl);
const surveyTextData = await surveyTextResponse.json();
// Returns: Aggregated text quality metrics for entire survey

// Platform-level text analysis summary
const platformTextUrl = `${API_BASE}/surveys/${surveyId}/platforms/${platformId}/text-analysis/summary`;
const platformTextResponse = await fetch(platformTextUrl);
const platformTextData = await platformTextResponse.json();
// Returns: Aggregated text quality metrics for platform within survey

// Respondent-level text analysis summary
const respondentTextUrl = `${API_BASE}/surveys/${surveyId}/platforms/${platformId}/respondents/${respondentId}/text-analysis/summary`;
const respondentTextResponse = await fetch(respondentTextUrl);
const respondentTextData = await respondentTextResponse.json();
// Returns: Aggregated text quality metrics for respondent

// Session-level text analysis (hierarchical V2)
const sessionTextUrl = `${API_BASE}/surveys/${surveyId}/platforms/${platformId}/respondents/${respondentId}/sessions/${sessionId}/text-analysis`;
const sessionTextResponse = await fetch(sessionTextUrl);
const sessionTextData = await sessionTextResponse.json();
// Returns: Complete text analysis details for specific session
```

**Tip:** Use hierarchical endpoints when you want aggregated reporting by survey/platform/respondent. Use the flat session endpoint for quick session-only lookups.

### Grid, Timing, and Fraud (Hierarchical V2)

The same hierarchy applies to **grid analysis**, **timing analysis**, and **fraud detection**:

- **Grid:** `GET /surveys/{survey_id}/grid-analysis/summary`, `.../platforms/{platform_id}/grid-analysis/summary`, `.../respondents/{respondent_id}/grid-analysis/summary`, `.../sessions/{session_id}/grid-analysis` — straight-lining, patterns, variance.
- **Timing:** `GET /surveys/{survey_id}/timing-analysis/summary`, and similarly at platform/respondent/session levels — speeders, flatliners, per-question timing.
- **Fraud:** `GET /surveys/{survey_id}/fraud/summary`, and similarly at platform/respondent/session levels — IP, device fingerprint, duplicate responses, velocity.

Grid and timing data are populated when you capture grid questions (section 3b) and when you call **composite-analyze** on completion (section 4). Fraud is computed as part of composite-analyze.

For full request/response shapes and all variants, see [API_V2.md](API_V2.md) or the main [API.md](API.md).
